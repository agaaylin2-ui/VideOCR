# AMD GPU porting plan

Audit date: 2026-11-13. Scope: VideOCR `master` at `548f8753d169539e56a0fb4ba532a53d8b7a8c82` and PaddleOCR-Standalone default branch at `6b9dca07636297b93fbb262b41af83caa2a13f4a`. These are independent source snapshots; VideOCR's build downloads the **latest release**, so the inspected standalone source is not proven to be the source of the binary a particular build consumes. Pin both releases, models and hashes before implementation. Source inspection and documentation review only: no models were converted, no OCR was run, and no GPU execution or accuracy was verified in this audit.

## Decision and feasibility

1. **Windows first:** prototype the exact PaddleOCR/PaddleX pipeline using ONNX Runtime (ORT) DirectML, with the existing CPU/CUDA standalone paths retained. This is promising, not demonstrated. PaddleOCR documents ONNX inference and conversion, but provider selection, actual model coverage, parity and packaging must be proven for the pinned standalone version. DirectML is in sustained engineering; Microsoft's newer WinML is worth a separate future evaluation, not a drop-in assumption for the existing Python executable. [DirectML documentation](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html), [PaddleOCR inference engines](https://www.paddleocr.ai/latest/en/version3.x/inference_deployment/local_inference/inference_engine.html).
2. **Linux:** reuse the same ONNX model and OCR contract with AMD's version-matched ORT MIGraphX execution provider (and evaluate the ROCm EP only where the selected AMD distribution provides it). AMD documents Radeon ORT installation; its 10.1 ecosystem matrix lists ORT/MIGraphX for Linux, not Windows, for specified architectures. Validate each GPU/OS/driver/framework combination. [AMD ORT instructions](https://rocm.docs.amd.com/projects/ai-ecosystem/en/latest/inference/onnxruntime.html), [AMD ecosystem matrix](https://rocm.docs.amd.com/en/latest/about/release-notes.html).
3. **Native Paddle on ROCm:** research track only. Paddle source contains `WITH_ROCM`/HIP build support, but the inspected default target list omits the target RDNA architectures and this audit did not find an official, supported PaddlePaddle binary and end-to-end PaddleOCR configuration for the RX 9070 XT on Linux or Windows. AMD ROCm hardware support does not establish Paddle framework support. Do not present a source build, a HIP SDK installation, or Windows ROCm availability as proof. [Paddle HIP configuration](https://github.com/PaddlePaddle/Paddle/blob/develop/cmake/hip.cmake), [AMD compatibility matrix](https://rocm.docs.amd.com/en/latest/compatibility/compatibility-matrix.html).
4. **CPU and NVIDIA:** retain their existing binaries, arguments, defaults and models as reference implementations. New GPU auto-selection must prove a provider is usable, report the selected device and fall back explicitly, never silently call a CPU run an AMD GPU run.

The `use_gpu` value is passed to the full OCR invocation but not the earlier detection-only invocation. Determine its actual provider at runtime before changing behavior; do not label that pass GPU-accelerated by inference. `stream_cli_process` drains stderr on a thread and exits on a nonzero child exit; it does not surface provider assignment or detect successful CPU partition fallback. Device checking by filename is fragile, and multiple candidate executable folders make the chosen binary dependent on directory enumeration.

## Standalone dependency and OCR data flow

VideOCR's entry points are `CLI/videocr_cli.py` and `CLI/videocr/api.py`. `find_executable` searches beside the program for `paddleocr-*` and `chrome-lens-*` executable folders. `resolve_model_dirs` selects bundled support files: PP-OCRv6 small/medium detection and recognition for its supported language groups; otherwise PP-OCRv5 mobile/server detection and language-specific mobile recognition, with PP-OCRv3 for Georgian, and `PP-LCNet_x1_0_textline_ori` for optional orientation. The exact `use_server_model` mapping is in `CLI/videocr/utils.py:215-255`; do not assume all languages use the same weights.

`Video.run_ocr` decodes and filters frames, constructs image grids, runs a detection-only subprocess, uses parsed polygons and SSIM filtering, and then runs either the Paddle `ocr` pipeline or Google Lens recognition; it maps grid geometry back to frames and generates/merges timed subtitles. Both Paddle subprocesses are batch invocations, with filenames delineated by `ppocr INFO: **********` and result lists parsed using `ast.literal_eval`. The Google Lens mode still uses Paddle detection. Preserve stitching, crops, dual zones, image saving, language/RTL handling, punctuation, confidence, timestamps and SRT postprocessing. Font assets are used for optional annotated images.

Standalone's `PaddleOCR-Standalone/Wrappers/{CPU,GPU-CUDA-11.8,GPU-CUDA-12.9}/wrapper.py` are Nuitka entry points setting PaddleX cache/source-check environment then calling `paddleocr.__main__.console_entry`. Standalone `paddleocr/_cli.py` dispatches subcommands; `_models/text_detection.py` provides detection, `_pipelines/ocr.py` constructs/predicts OCR, `_pipelines/base.py` calls PaddleX `create_pipeline`, and `_common_args.py` passes device/engine. Standalone `pyproject.toml` requires `paddlex[ocr-core]>=3.7.0,<3.8.0`; the checked-in code recognizes `onnxruntime` engine and `--engine`, but this does **not** prove the released artifact, PaddleX version, model directories, DirectML provider configuration or parseable output work together. The wrapper embeds its own dependencies. Its `.github/workflows/test_gpu.yml` explicitly uses `nvidia-smi`, NVIDIA CUDA image and CUDA Paddle wheel; its installer scripts are CPU/CUDA-specific. The complete inherited PaddleOCR tree has many CUDA references, including training/deployment examples; those are outside VideOCR's inference path, not requirements to port wholesale. Inspect standalone release/build recipe and artifact contents because a reproducible binary build recipe and actual Paddle wheel selection are not established by wrapper metadata alone.

## ONNX feasibility and proof gates

PaddleOCR officially documents PaddleX/Paddle2ONNX conversion and `engine="onnxruntime"`. Conversion may automatically select a higher opset; DirectML documentation states support through opset 20 with exceptions. Record actual opset, dynamic dimensions, operators and model SHA-256; validate rather than assume. [Conversion guide](https://www.paddleocr.ai/latest/en/version3.x/inference_deployment/others/obtaining_onnx_models.html), [DirectML provider](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html).

1. Freeze the exact release support archive, extract model configs and dictionaries, inventory every selected det/rec/cls model by name and hash. Convert each variant, retaining preprocessing metadata, character vocabulary, decoder and original weights. Bundle a versioned mapping/manifest; check redistribution licenses and size. Cover v6 small/medium, v5 script-specific/server/mobile and v3 Georgian as applicable, plus orientation. Do not claim conversion success for all models from documentation alone.
2. First try PaddleOCR/PaddleX's ONNX engine with explicit provider configuration while retaining its preprocessing, detector DB postprocessing, recognition decoding, thresholds and CLI result adapter. Confirm the installed PaddleX release exposes the necessary DirectML/MIGraphX configuration and builds sessions for both commands; if it does not, implement a small isolated standalone adapter using the same upstream preprocessing/postprocessing. Merely adding `--engine onnxruntime` or installing `onnxruntime-directml` is not proof of provider selection.
3. Compare Paddle CPU FP32 to ORT CPU FP32 on identical images, then ORT GPU against ORT CPU: tensors with tolerances, polygon IoU/order, text and confidence, classification and full SRT. Compare all model groups and non-Latin scripts. Record failed conversions, unsupported operators and provider partitions. Start FP32; only consider FP16 or quantization after accuracy gates.
4. On Windows create sessions with `DmlExecutionProvider` and an explicit DXGI adapter ID; DirectML requires sequential execution, memory pattern disabled, and no concurrent `Run` on one session. A multi-GPU system's adapter 0 may be an iGPU. Package the correct Windows ORT binary and dependencies. On Linux choose a compatible AMD wheel, driver and MIGraphX libraries, with exact OS/Python/ROCm constraints. Provider availability and session provider list are necessary but insufficient: collect ORT node-level profiling/assignment showing meaningful det and rec compute on the intended AMD adapter plus independent GPU activity under real inference. Identify CPU-resident preprocessing and fallback partitions. Fail strict GPU tests if all meaningful work runs on CPU.

## Compatibility risks

| Target | Assessment |
|---|---|
| RX 6000 / RDNA 2 | DirectML hardware class is broad but each card/driver still needs a real test. AMD's ROCm matrix lists selected RDNA2 PRO devices; do not infer consumer RX 6000 series support or ORT/MIGraphX support from family membership. Treat Linux support as unverified unless exact SKU appears in the relevant version's full stack matrix. |
| RX 7000 / RDNA 3 | Selected SKUs are listed by AMD for ROCm; support varies by SKU, gfx target, OS and release. Test at least distinct supported gfx1100 and gfx1101 where available; other models require separate proof. |
| RX 9000 / RDNA 4 | RX 9070 XT is gfx1201, 16 GB, and AMD lists it for selected ROCm releases. This proves platform eligibility only, not Paddle, model operator or VideOCR compatibility. Test gfx1200 separately. |

AMD's versioned Radeon matrix, not generic architecture names or overrides such as `HSA_OVERRIDE_GFX_VERSION`, determines support claims. Windows AMD ROCm/HIP and WSL have their own matrices and framework constraints; no officially validated Windows Paddle-on-ROCm path was established. Driver changes, dynamic shapes, unimplemented operations, CPU partition copies, graph compilation latency, dtype, memory and third-party wheel ABI are material risks. [AMD ROCm 10.1 matrix](https://rocm.docs.amd.com/en/latest/compatibility/compatibility-matrix.html), [AMD 9070 XT specifications](https://rocm.docs.amd.com/en/latest/reference/gpu-specs.html), [versioned Radeon 7.1.1 matrix](https://rocm.docs.amd.com/projects/radeon-ryzen/en/docs-7.1.1/docs/compatibility/compatibilityrad/native_linux/native_linux_compatibility.html).

## Proposed backend contract and fallback

Keep engine choice (`paddleocr` vs Google Lens recognition) separate from execution backend. Add a versioned adapter interface with `capabilities()`, `initialize(model_manifest, device)`, `detect(images)`, `ocr(images, orientation)`, `close()` and typed result objects carrying image ID, polygon, text, confidence and ordering. The adapter must cover standalone detection for both engine modes, full OCR and optional output images. Preserve process isolation: wrap the existing executable unchanged as the legacy Paddle CPU/CUDA adapter; add an ONNX worker in a separately packaged environment to avoid dependency and DLL collisions. Prefer versioned JSON Lines over parsing human logs for the new worker; keep legacy parsing behind its adapter. Preserve cancellation, child exit diagnostics and existing temporary file lifecycle.

Expose `auto`, `cpu`, `cuda`, `directml`, `migraphx` and optional `rocm` only when implemented; allow an explicit device/adapter ID. Maintain `--use_gpu true/false` compatibility (false = CPU; true selects an available compatible accelerator, with legacy CUDA priority on an existing NVIDIA build); reject contradictory flags. Preserve GUI default and saved checkbox meaning through migration. In `auto`, rank available packaged accelerator candidates according to OS, installed device and existing CUDA preference, run a bounded initialization and real representative model inference probe, then use CPU if none passes. Explicit backend requests fail clearly by default; provide an explicit opt-in fallback flag. Show/log requested and actual provider, device, driver, model, partitions and fallback reason. Do not infer execution from device enumeration. A later runtime failure must discard incomplete stage results and restart the stage cleanly on CPU, or fail with a clear error; never merge partial attempts, duplicate subtitles or silently change a forced backend.

## Exact implementation touchpoints

**VideOCR (existing):** `CLI/videocr/api.py` (resolve policy and adapter); `CLI/videocr/utils.py` (deterministic discovery, backend-specific probes and typed child failures; preserve AVX requirements for binaries that need them); `CLI/videocr/video.py` (route both passes through adapter without changing frame/subtitle logic); `CLI/videocr_cli.py` (flags, compatibility and diagnostics); `VideOCR.py` (backend/device selector, settings migration and actual status); `languages/*.json` (translated labels/help); `build.py` (pinned artifacts, hashes, manifests, naming and targets); `pyproject.toml` (only dependencies actually required by the app/build; isolate worker runtime); `Dockerfile` (add explicitly selected AMD build/runtime path without replacing CPU/CUDA); `.github/workflows/docker.yml` (matrix and gated release); `.github/workflows/pre-commit.yml` (CPU contract tests); `README.md`, `README_ch.md`, `.github/ISSUE_TEMPLATE/bug_report.yml` (supported matrices, diagnostics, fallback); `Installer/Windows/installer_template.iss`, `Installer/Linux/install_videocr.sh`, `Installer/Linux/uninstall_videocr.sh` (only if layout/naming changes require it).

**New proposed paths:** `CLI/videocr/backends/{__init__,base,legacy_paddle,onnx_worker,discovery}.py`; `tests/` for contract, integration, model parity and fixtures; `benchmarks/` for repeatable harness/results schema; `models/manifest.json` or equivalent release manifest; `scripts/export_onnx.py` and lock files. Names are proposed, not existing files.

**Standalone fork (if using a new worker):** `PaddleOCR-Standalone/Wrappers/` add an ONNX worker entry point and packaging metadata; `paddleocr/_common_args.py`, `paddleocr/_pipelines/base.py`, `paddleocr/_models/text_detection.py`, `paddleocr/_pipelines/ocr.py` only if the pinned PaddleX API cannot pass provider selection or expose structured results cleanly; prefer an external wrapper over maintaining upstream patches. Add reproducible dependency/build scripts and relevant tests. Existing `PaddleOCR-Standalone/Installer/*.iss`, `pyproject.toml` and GPU workflow change only if producing/distributing the standalone variant there. The release binary and support archive must be pinned as a tested set.

## Phases and release gates

0. **Baseline:** pin commits, released artifacts, dependencies/models/hashes; capture CPU and CUDA golden results and actual detection device, supported features, memory/time. Acquire permitted representative clips and ground truth. Gate: reproducible builds and baseline recorded.
1. **Feasibility spike:** convert representative v6 small det/rec, v5 script rec and optional cls; run Paddle CPU vs ORT CPU, then Windows RX 9070 XT DirectML. Gate: matching results, verified node placement and real end-to-end run; explicitly enumerate unsupported variants. No public acceleration claim before this gate.
2. **Contract and regressions:** extract adapter, deterministic discovery, explicit selection and fallback; wrap existing CPU/CUDA; test unchanged behavior, Google Lens detection and existing flags. Gate: golden SRT and packaged CPU/NVIDIA regressions pass.
3. **Windows preview:** package DirectML worker and converted models, validate selection, fallbacks, multilingual parity, clean installation and GUI/CLI. Gate: evidence of execution plus accuracy and feature gates below. Label experimental until tested hardware matrix is published.
4. **Linux preview:** select a documented Radeon/OS/driver/ROCm/ORT/MIGraphX combination; package a separate reproducible worker and optional AMD image. Container instructions must expose `/dev/kfd` and appropriate `/dev/dri` render devices with required permissions, matching host driver and userspace; never use NVIDIA `--gpus all` as AMD setup. Gate: same execution and quality evidence and clean CPU fallback. Native Paddle ROCm remains an independent feasibility experiment.
5. **Expand/release:** convert and validate every model selection before claiming full language coverage; broaden RDNA SKU matrix, package signed artifacts, checksums and license notices; publish measured results, supported and untested combinations, and rollback instructions. Do not remove CPU/CUDA artifacts.

## Test and benchmark plan

- Unit/contract: legacy argument mapping, deterministic executable lookup, multiple adapters, missing provider/runtime, unsupported GPU, strict selection, explicit CPU, model manifest mismatch, startup and mid-run failure, cancellation, no partial/duplicate results, structured protocol, text/geometry/confidence and GUI config migration. Ensure `--use_gpu` behavior remains compatible and conflicts are diagnosed.
- Golden integration: fixed licensed videos and image fixtures with manually checked SRT, languages from each v6/v5/v3 group including CJK, Arabic/RTL, accented Latin and Georgian; detection/recognition/optional orientation, low confidence and tiny/stylized text, motion/scene cuts, varying resolutions, dense/multiline and empty frames, cropped/dual zones, stitching on/off, server/mobile, OCR image output and Google Lens detection. Mock external Lens in CI and exercise the existing integration separately where available. Compare raw boxes, recognized characters, confidence and final timing/alignment, not only a successful process.
- Accuracy: establish baseline first, then predeclare thresholds; initial proposed gate: no statistically meaningful regression in corpus-level character error rate (CER) and word error rate (WER), no per-language CER increase >1 percentage point without review, detection F1 drop <=1 percentage point at matched IoU, subtitle cue timing median and p95 differences <= one sampled-frame interval, and no systematic missing/duplicate cues. Document ground truth, normalization and confidence intervals; strict golden cases require exact expected cues. Thresholds are proposals, not observed results.
- Hardware matrix: RX 9070 XT Windows DirectML and supported Linux ROCm/MIGraphX first; representative supported RDNA3 devices and available RX 6000 on DirectML; NVIDIA CUDA 11.8/12.9 supported machines and CPU on Windows/Linux. Record exact model, GPU PCI/adapter ID, OS/kernel, driver, ROCm, ORT/EP, PaddleX, Python, model hash, clocks/power and provider node assignment. Unsupported hardware is recorded as such, never silently promoted to supported.
- Performance: same clips/options on CPU, existing NVIDIA baseline and AMD; cold initialization/model conversion/load and graph compilation separately from warm detection, OCR and end-to-end wall time, processed frames/s, video real-time factor, per-stage p50/p95, peak RAM/VRAM, fallback fraction and output quality. Warm up, run at least five measured repetitions, report median and spread; control cache, input and power conditions. Compare same models/precision/settings, not GPU vs a weaker CPU model. Profile partitions and transfers; speedup alone does not prove GPU inference.
- CI: hosted Windows/Linux run unit, ORT CPU conversion/parity and packaged CPU smoke tests with pinned fixtures. Hardware-labelled trusted runners run scheduled/manual CUDA, DirectML and ROCm tests with captured profiling and accuracy artifacts; do not run untrusted pull-request code on privileged self-hosted machines. Release jobs depend on successful hardware gates for each advertised artifact. No runner or matching hardware means mark that target unverified, not passed.
